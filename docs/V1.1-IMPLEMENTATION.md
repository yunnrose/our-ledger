# Our Ledger v1.1 — shared-link identity mode

## Confirmed product decision
- Both people use the same shared URL.
- On entry, each person chooses either `我是佩筠` or `我是 Benson`.
- The selection is stored in browser localStorage and can be changed with the header button.
- This is a self-declared display/operator label, **not verified personal identity**. Anyone with the shared URL can choose either name. Audit records therefore prove only what the browser session declared, not who physically performed the action.

## Implemented on this branch
- Firebase Anonymous Authentication creates an anonymous session for the shared browser without requiring email/password accounts.
- The user selects the display/operator identity after the session starts; the selection is stored locally in `ledger_operator`.
- The anonymous Firebase UID and selected operator label are included in audit events.
- Existing Realtime Database paths `transactions/` and `logs/` are retained.
- Expense creation, edit, settlement and void operations record actor metadata.
- Voiding is a soft delete (`isDeleted: true`); rows remain in the database and are excluded from chat and balance calculations.
- Safe DOM rendering uses DOM nodes and `textContent` for user/database-controlled content.
- Taiwan-local dates are used for new records.
- Natural-language expense parsing and ledger calculations are separated into `js/ledger-core.js`.
- Legacy settlement rows without `receiver` and fractional historical amounts remain supported.
- New entries accept integer TWD amounts; pending entries are excluded from confirmed totals and settlement.

## Required Firebase Console setup
1. Firebase Console → Authentication → Sign-in method → enable **Anonymous** provider.
2. Copy the Firebase Web App configuration from Project settings → Your apps.
3. Create local `js/firebase-config.js` from `js/firebase-config.example.js` and replace the placeholders. The real project config is not committed by this branch.
4. Export the complete current Realtime Database JSON and existing Rules before publishing new rules.
5. Review `database.rules.example.json` before publishing. It allows any authenticated Firebase session to read/write `transactions/` and `logs/`. Since Anonymous Authentication is open to anyone, this does **not** restrict access to only the two intended people. Anyone who can reach the app and complete anonymous sign-in can access the shared ledger.
6. Test the app with both people on separate browsers/devices. Confirm identity selection, real-time sync, edits, voids, settlement and legacy rows.

## Security and privacy limitations
- Choosing a name in the UI does not authenticate that person. Either person can impersonate the other by selecting the other name.
- The anonymous UID distinguishes browser sessions, not the two people. It is not a substitute for individual accounts.
- Do not describe audit entries as non-repudiable identity evidence.
- If access must be restricted to exactly two people, use individual Firebase Authentication accounts and UID allowlisting instead.
- Firebase App Check may reduce abuse from clients outside the deployed app, but it does not prove whether the visitor is 佩筠 or Benson.
- Never commit service-account JSON, private keys, passwords, or ID tokens.

## Data protection and rollout
- Export the entire Realtime Database (including `transactions`, `logs`, and all other paths) before changing production Rules.
- Store backups outside this repository in a private, access-controlled location.
- Do not clear, rewrite, or regenerate existing transaction rows. Preserve IDs and legacy fields.
- Test against a separate Firebase project first; do not use production data for write tests.
- Rollback by redeploying the previous application and restoring the exported Rules. Restore JSON only if data was changed or corrupted.


## Release gate
- Firebase Anonymous provider enabled.
- Correct Firebase Web App config supplied locally/through hosting.
- Production JSON and Rules exported and secured.
- Rules reviewed with awareness that anonymous access is open to any app visitor.
- Both people have tested the shared URL on separate devices.
- Domain tests pass.
- Production branch remains unchanged until approval.
