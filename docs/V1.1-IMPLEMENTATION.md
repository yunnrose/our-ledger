# Our Ledger v1.1 — implementation and rollout

## Implemented on this branch
- Individual Firebase Email/Password sign-in; identity is resolved from the authenticated UID, never from a browser-side identity switch.
- The authenticated UID must have an active member profile at `members/{uid}` with `{ "name": "佩筠" | "Benson", "active": true }`.
- Existing Realtime Database paths `transactions/` and `logs/` are retained.
- Expense creation, edit, settlement and void operations record the authenticated actor UID/name in the audit log.
- Voiding is a soft delete (`isDeleted: true`); transaction rows are retained and excluded from chat and balance calculations.
- Safe DOM rendering uses `textContent`/DOM nodes for user- and database-controlled content.
- Taiwan-local date/time is used for new records.
- Natural-language parsing and ledger calculation are separated into `js/ledger-core.js`.
- Existing settlement rows without `receiver` remain supported; fractional legacy amounts remain included in totals.
- New entries accept integer TWD amounts; pending entries are excluded from confirmed totals and settlement.

## Required Firebase Console setup (not yet performed)
The repository currently has only a Realtime Database URL. Firebase Authentication cannot be enabled from this code repository. A project administrator must complete these steps:

1. Firebase Console → Authentication → Sign-in method → enable **Email/Password**.
2. Create two users (one email/password login for each person). Do not commit passwords or send them in chat.
3. Copy the Firebase Web App configuration from Project settings → Your apps.
4. Create `js/firebase-config.js` locally by copying `js/firebase-config.example.js` and replacing the placeholders with the Web App config. This file is intentionally not created with fake values.
5. For each created Authentication user, copy its UID. In Realtime Database, create:
   - `members/{PEIJUN_UID}` = `{ "name": "佩筠", "active": true }`
   - `members/{BENSON_UID}` = `{ "name": "Benson", "active": true }`
   Keep `members` writes administrator-only.
6. Review and export the current Realtime Database rules. Only after confirming both UIDs and backing up existing data, publish the rules from `database.rules.example.json`. They permit reads/writes only for authenticated UIDs with an active member record.
7. Test both accounts in separate browser profiles. Confirm unauthenticated users cannot read or write, and a signed-in non-member is denied.

The `apiKey` and Firebase Web App identifiers are client configuration, not service-account secrets. Never place service-account JSON, private keys, passwords, or ID tokens in this repository.

## Data protection and rollout
- Export the complete Realtime Database JSON (including `transactions`, `logs`, and any other paths) before changing production rules.
- Store the export in a private, access-controlled location outside this repository.
- Do not clear or rewrite legacy transaction rows. Existing IDs and fields are preserved.
- Test on a separate Firebase project first. Do not test writes against production data.
- Verify old transactions, old settlements without `receiver`, pending items, and historical fractional amounts.
- Keep the production branch unchanged until the two-account test passes.
- Rollback: redeploy the previous application and restore the exported rules. Restore the JSON backup only if a data migration or accidental data mutation occurred.

## Automated domain tests
Run in a local checkout with Node.js:
```sh
node --test tests/ledger-core.test.js
```

## Current limitations / next v1.1 gate
- Firebase Auth and member allowlist are implemented in the client flow and example rules, but **cannot become live until the Firebase Console setup above is completed**.
- The Firebase Web App config is deliberately absent; copy the example file to `js/firebase-config.js`.
- Rules have not been published and no production database has been modified by this branch.
- Before production release, verify the Firebase config file is excluded from Git if your deployment workflow requires a local config file, and add it through your private hosting environment instead.
